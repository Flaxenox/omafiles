There is no "Gemini" author anywhere in history. Any prior "Gemini did X" framing is shorthand, not fact. Below, "the post-Phase-30 refactor era" refers to work done under these real git identities.

**Gap found and filled:** neither source report examined `core/ControllerRegistry.qml`. Its own header comment dates it to **Phase 11.C** (i.e., inside the pre-30 window report 1 covers, but not caught by it) and states its purpose in the maintainer's own words: *"SOLE owner of all the logic/ controllers (Phase 11.C, josema: eradicate the scattered ownership that the 2026-08-09 audit flagged). Before, OmafilesContent instantiated the 22 controllers + used them by id as a god object; now it instantiates them here and receives them by property."* This is a real, independently-verifiable architectural event missing from both reports — added to the timeline below as the Phase 11.C row.

## 3. Per-Change Verdict: Improved, Merely Changed, or Removed a Useful Boundary?

**Improved the original architecture (boundary strengthened or complexity genuinely reduced, verified):**
- **Phase 34.1** (`services/` proxy deletion) — the proxy layer was pure 1:1 indirection with no behavioral purpose once the C++ backend existed directly under a stable module name; removing it deleted ceremony, not a boundary. Verified gone at HEAD.
- **Phase 34.4** (ActionEngine's *first*, pre-merge optimization) — signal/callback overhead genuinely reduced, file got *smaller*, verified by line count.
- **Phase 34.5** (drop `inotifywait` fallback) — removed an external runtime dependency and an orphan-process risk class entirely; the native `QFileSystemWatcher` is strictly more contained. Verified gone.
- **Phases 36–38, 42.1–42.3** (pygments, ffprobe, content-search.sh, empty-trash.sh, open-with-list.sh, xdg-terminal-exec, gio mount → native C++) — this is the most consistently verified pattern in the whole history: six separate subprocess-to-native migrations, and in every single case the grep confirms the old shell invocation is gone, not just superseded. This is boundary-respecting migration exactly as `BACKEND_DESIGN.md` intended: the QML-facing API didn't change, the backend absorbed the responsibility, the old escape hatch was actually removed rather than left as debt.
- **Phase 41** (FileOperations/Sidebar/SyntaxHighlighter/MediaInfo split into submodules) — this is decomposition done with full ceremony: an independent audit with maintainability/build/risk scores, every resulting file verified present and within the 300-500 line design cap. It is the *positive* mirror-image of the `37f3f31` merge, executed in nearly the same commit range.
- **Phase 11.C** (`ControllerRegistry` creation) — a genuine, successful fix for exactly the kind of "god object" problem that later recurs at `37f3f31`, but solved here by consolidating *ownership* (who instantiates the controllers) without consolidating *code* (the controllers stayed as separate files). This is the counter-example that makes the `37f3f31` approach look like an unforced regression rather than the only available fix.

**Merely changed shape (net-neutral, not a regression but not obviously an improvement either):**
- **Fase 4's dual-frontend service duplication → Aug 9's shared-backend collapse → Aug 10's dual-frontend abandonment.** Read end-to-end, this is a five-day round trip: build for two frontends, unify their backend, then delete one frontend entirely. Not wasted motion exactly — the backend unification work (Phase 5, all of Aug 9) is what made the native C++ layer exist at all, and that layer outlived the dual-frontend rationale that justified building it. But the *specific* per-host `services/+standalone/` duplication from Fase 4 was pure churn: built, then deleted 4 calendar days later, before ever shipping a stable release with two live frontends.
- **Phase 34.2's OmafilesContent slimming** — the boundary intent (thin composition root, no pass-through wrappers) is sound and matches the project's own stated goals; the fact that it briefly broke `ActiveFileList.qml` is an execution defect, not a design flaw, and it was caught in one commit.

**Accidentally (or non-transparently) removed a useful boundary:**

  1.   2.   3.   4. It is publicly acknowledged, but only as a one-line, framing-loaded `CHANGELOG.md` entry ("Flatter QML object graph... highly cohesive ActionEngine.qml") that does not mention the prior audit it overrides.
  5. The result — 1205 lines, 67 functions, 4x the project's own stated file-size guideline — is objectively the kind of file the project's design docs, risk audits, and Phase 41 sibling-effort all argue against, independent of whether the tests currently pass (85/85 selfchecks, verified: `grep -rh "sc.add(" src/selfcheck/checks/*.qml | wc -l` = 85).

  This is a regression in the architectural sense the audit is asking about — not "the code is broken" (no evidence found that it is), but "a documented boundary, defended in writing once already, was removed without the scrutiny the project applies to every comparable change, and without acknowledging the removal contradicts its own prior risk assessment."
