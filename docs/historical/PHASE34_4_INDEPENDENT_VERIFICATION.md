## 2. Signal Wiring Verification

### Direct Codebase Inspection
- Grep queries across `logic/ActionEngine.qml` confirm that **0 dynamic `connect()`** and **0 dynamic `disconnect()`** calls remain.
- All interactions with `Backend.FileOperations` (`progress`, `finished`, `error`) are now routed through a single, static declarative `Connections` object:

```qml
Connections {
  target: Backend.FileOperations

  function onProgress(op, path, done, total) {
    if (!nativeBusy || _progTotal <= 0) return
    _lastItemTotal = total
    ActionState.actionProgressPct = Math.min(100, (_progBase + done) * 100 / _progTotal)
  }

  function onFinished(op, path) {
    if (!nativeBusy) return
    _progBase += _lastItemTotal
    _lastItemTotal = 0
    _batchIdx += 1
    _batchNext()
  }

  function onError(op, path, msg) {
    if (!nativeBusy) return
    if (msg && msg !== "cancelled")
      Backend.Notifier.notify("Action failed: " + msg)
    _finishNative(false)
  }
}
```

### Signal Boundary Safety
- **Stale Signal Immunity:** Every slot in `Connections` begins with `if (!nativeBusy) return`. Signals generated by background threads, external callers, or completed operations cannot trigger unintended batch advancement.
- **ProcessRunner Handling:** `Backend.ProcessRunner` (`actionProc`) continues to use its native declarative `onFinished` property binding. No hidden dynamic connections exist.

## 3. Batch Semantics Verification

The batch state machine was traced through all execution paths:

1. **Sequential Progression:** `_batchIdx` increments only inside `onFinished`. Each item is submitted sequentially via `_batchNext()`, preserving the exact sequential execution order of prior versions.
2. **Error Semantics:** When `onError` triggers, the engine logs the notification (unless aborted via `"cancelled"`) and immediately invokes `_finishNative(false)`, preventing subsequent batch items from executing. This matches `st=1; exit $st` fail-fast semantics.
3. **Cancellation Path:** `cancelAction()` sets `_cancelling = true` and invokes `Backend.FileOperations.cancel()`. The C++ worker emits `error(op, path, "cancelled")`, which is intercepted and cleanly concludes the batch.
4. **Operation Dispatch:** `_batchNext()` routes identically across operations:
   - `"remove"` $\rightarrow$ `Backend.FileOperations.remove(p.src, _batchOverwrite)`
   - `"trash"` $\rightarrow$ `Backend.FileOperations.trash(p.src)`
   - `"restore"` $\rightarrow$ `Backend.FileOperations.restoreByOrigPath(p.src)`
   - `"move"` $\rightarrow$ `Backend.FileOperations.move(p.src, p.dest, _batchOverwrite)`
   - `"copy"` $\rightarrow$ `Backend.FileOperations.copy(p.src, p.dest, _batchOverwrite)`

## 4. Re-Entrancy Analysis

### `Qt.callLater(cb)` in `_finishNative`
- **Previous Behavior:** The `onDone` callback was called synchronously inside the signal handler during the active signal dispatch loop of `Backend.FileOperations`. If the callback immediately scheduled another operation (e.g. `c.undoLast()` running `restore` after `trash`), new listeners attached during the signal dispatch could be exposed to the active signal emission.
- **Optimized Behavior:**
  - `nativeBusy = false` and `_resetActionState()` execute **synchronously**, putting the UI and state singletons into an immediate idle state.
  - `Qt.callLater(cb)` defers user callback execution to the start of the next event-loop tick.
- **Impact Assessment:**
  - `ActionState.actionBusy`, `ActionState.actionLabel`, and `ActionState.actionProgressPct` update synchronously with zero visual lag or flicker.
  - Subsequent asynchronous operations initiated by `cb()` start with a clean C++ signal dispatcher state.
  - No ordering inversions or UI timing issues were observed.

## 5. State Cleanup Verification

The newly extracted `_resetActionState()` helper:
```qml
function _resetActionState() {
  ActionState.actionBusy = false
  ActionState.actionLabel = ""
  ActionState.actionProgressPct = -1
  navController.refresh()
  NavState.refreshTick += 1
}
```
Is called unconditionally in:
1. `cancelAction()` (shell fallback path)
2. `_finishNative()` (native batch completion & failure paths)
3. `actionProc.onFinished` (shell process completion path)

All 5 core state mutations are preserved in every teardown scenario.

## 6. Performance Assessment

### Quantified Improvements
1. **Closure Allocations:** Prior to optimization, a batch of $N$ items allocated $3N$ JavaScript function objects (`ok`, `bad`, `cleanup`) on the V8/QML JS heap. With static `Connections`, closure allocation per batch item is **0**.
2. **C++ Connection Tree Churn:** Prior to optimization, $2N$ `QMetaObject::Connection` registrations and disconnections were processed by Qt's signal connection tables. This is now reduced to **0 dynamic connections**.
3. **Source Code Reduction:** File size decreased from **311 lines** to **268 lines** (**-43 lines / -13.8%**).

### Practical Impact
- For small operations (1–2 files), the performance gain is in microseconds.
- For large file batches (hundreds to thousands of files during large drag-and-drop, cut/paste, or multi-item trash ops), this optimization eliminates garbage collection pressure on the QML UI thread and avoids mutating Qt's connection lists during active I/O loops.
